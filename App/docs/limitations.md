# Ограничения и известные проблемы

## Границы стенда

- **Все контейнеры на одном хосте.** Падение хоста останавливает всё. Для демонстрации этого достаточно,
  для настоящей работы нужны несколько хостов и база с репликацией.
- **Режим настоящих машин не реализован.** Поля SSH (`ssh_host`, `ssh_port`, `ssh_user`, `ssh_key_ref`)
  есть в модели и API, но запуск и обновление агента по SSH не сделаны: узлы поднимаются как контейнеры
  (Э6 плана, раздел 2.2). Терминал, соответственно, идёт в контейнер через `docker exec`, а не по SSH.
- **Внутри сети стенда соединения без TLS:** nginx → api, api → runner, api → база и Redis. Снаружи
  открыт только nginx. На нескольких хостах это пришлось бы закрыть.
- **Настоящий внешний сайт не проверялся.** Вся проверка идёт на заглушке и управляемом тестовом сайте.
  Перед работой с настоящим сайтом обязательно снизьте `COORD_GLOBAL_RPS_LIMIT`: на стенде он 3000.

## Лимиты и производительность

- **Один процесс `api` с лимитом 1 CPU** держит примерно 160 запросов в секунду. На 60 агентах ответ
  интерфейса доходит до 6,5 с, а задержанный heartbeat может ошибочно снять блок с живого узла. Работа
  не теряется, но часть результатов пересчитывается. Решение: `COORD_API_WORKERS` и `COORD_API_CPUS`,
  цифры в [отчёте о нагрузке](load-report.md).
- **Лимит запросов обновляется раз в секунду,** новый узел получает оценку доли до следующего прохода
  диспетчера. Поэтому в первую секунду сумма долей может ненадолго превысить лимит.
- **Лимит запросов один на весь стенд,** задание может его только снизить. Раздельных лимитов на
  проверку страниц и загрузку файлов на стороне координатора нет: это настройки агента (ТЗ, п. 9).
- **Память контейнера считается вместе с кэшем файлов** (`memory.current` в cgroup). Агент, активно
  пишущий файлы, может показывать загрузку памяти выше фактической, поэтому порог отказа в выдаче 97 %.
- **Метрик хоста и `docker stats` нет,** только то, что сообщает сам агент из cgroup. Перезапуски и
  OOM-kill видны через runner. Часть метрик ТЗ, п. 12 (своп, дисковый ввод-вывод, открытые файлы) платформа
  примет и сохранит в `extra`, если агент их пришлёт, но отдельных графиков для них нет.

## Настоящий агент

- **Прогресс загрузки каждого файла в интерфейсе не показывается.** Агент не сообщает о загрузках в
  процессе, платформа видит файл только по результату. Поля `active_checks` и `active_downloads`
  отображаются, если агент их присылает; сейчас это делает только заглушка.
- **Новое число потоков** настоящий агент применяет со следующего блока и в пределах своей настройки
  `check_concurrency`, а не сразу.
- **Отмена блока** у настоящего агента срабатывает после завершения уже начатых элементов.

## Терминал

- **Журнал видит набранное, а не выполненное.** История по стрелкам и автодополнение ему не видны, поэтому
  политика опасных команд — страховка от ошибки, а не граница безопасности. Границы безопасности — роль
  администратора и непривилегированный пользователь внутри контейнера.

## Интерфейс и данные

- **Несколько заданий одновременно делят один лимит и один набор узлов.** Блоки выдаются в порядке номеров
  заданий, приоритетов нет.
- **Узел нельзя удалить из интерфейса,** только отключить: на него ссылается история элементов и событий.
- **Метрики хранятся 24 часа, снимки скорости 4 часа, события 30 дней.** Элементы и аудит не удаляются.
  Для долгой работы таблицу `items` стоит разбить на секции.
- **Индивидуальные потоки при создании задания** задаются через API (`workers` в `POST /api/jobs`), а в
  интерфейсе через настройки узла, отдельного поля в форме задания нет.

## Предупреждения сборки

- Starlette предлагает заменить `httpx` на `httpx2` в тестовом клиенте. На работу не влияет.
