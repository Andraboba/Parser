# Сценарий демонстрации (ТЗ, п. 23)

Весь сценарий идёт без настоящего внешнего сайта. Заглушки имитируют агентов, а для демонстрации с
настоящими агентами есть управляемый тестовый сайт.

## Подготовка

```bash
bash scripts/init-env.sh
```

С заглушками:

```bash
docker compose up -d --build
```

Или с настоящими агентами и тестовым сайтом, в этом случае он отдаёт в том числе 403, 429 и 500:

```bash
docker compose -f compose.yaml -f deploy/compose.real-agent.yaml up -d --build
```

Откройте https://localhost:8443 и войдите как `admin`. Для графиков запустите мониторинг:

```bash
docker compose --profile monitoring up -d
```

## Шаги

Команды `exec` ниже управляют заглушкой через её управляющий файл. Для настоящих агентов шаг 10 не нужен:
тестовый сайт и так отвечает 429 на каждый десятый идентификатор.

**1. Координатор и тестовый сервис запущены.** `docker compose ps`: всё `healthy` или `running`.

**2. Три узла с разным числом потоков.** Страница «Узлы»: 8, 16 и 2 потока, разные лимиты CPU и памяти.

**3. Конечный диапазон.** «Задания» → диапазон `[1,200000]`, размер блока `1000` → «Создать» → «Запустить».

**4. Динамическая выдача.** «Журнал»: чередуются `chunk.lease` разных узлов, причём сильный узел берёт
блоки чаще. На «Панели» растёт прогресс.

**5. Найденные материалы и файлы.** Страница задания → «Все элементы», фильтр «Загружено»: метаданные,
размер, путь к файлу. Файл действительно на месте:

```bash
docker compose exec worker-01 sh -c "ls /data/videos | head"
```

**6. Отказ узла.**

```bash
docker compose stop worker-02
```

**7. Блок передан другому.** Примерно через 10 секунд на странице «Узлы» `worker-02` показывает «Нет
связи», на «Панели» появляется предупреждение. В «Журнале» фильтр по тексту `возврат`: событие
`chunk.reclaimed` и контрольная точка, с которой блок продолжит другой узел.

**8. Узел возвращается.** Он снова начнёт получать блоки.

```bash
docker compose start worker-02
```

**9. Потоки без остановки.** Страница `worker-01` → настройки → потоков `4` → «Сохранить». Следующий
heartbeat донесёт значение до агента. Или страница задания → «Параметры» → «Изменить на ходу».

**10. Ответ 429 снижает частоту.**

```bash
docker compose exec worker-02 sh -c "echo '{\"rate_limited\": true}' > /tmp/stub-control.json"
```

На дашборде Grafana падает панель «Общий лимит запросов», на панели скорость снижается, появляется
предупреждение про 429. Снимите имитацию, лимит вернётся за несколько десятков секунд:

```bash
docker compose exec worker-02 rm /tmp/stub-control.json
```

**11. Нехватка места.**

```bash
docker compose exec worker-01 sh -c "echo '{\"disk_free_bytes\": 1000}' > /tmp/stub-control.json"
```

Страница `worker-01`: «Новые блоки не выдаются: мало свободного места». Остальные узлы продолжают работу.
Верните как было:

```bash
docker compose exec worker-01 rm /tmp/stub-control.json
```

Настоящее заполнение диска на tmpfs показывает сценарий `python scripts/chaos.py real_disk_full`.

**12. Перезапуск координатора.** Прогресс на панели не откатывается, задание продолжается.

```bash
docker compose kill api
```

```bash
docker compose up -d api
```

**13. Целостность и отсутствие дубликатов.** После завершения задания обработано ровно 200 000, сумма
статусов элементов тоже 200 000. Проверка прямо в базе, запрос вернёт ноль строк:

```bash
docker compose exec db psql -U coord -c "SELECT job_id, external_id, count(*) FROM items GROUP BY 1,2 HAVING count(*) > 1"
```

**14. Метрики, журнал и аудит.** «Журнал» с поиском по заданию и узлу. «Аудит»: кто запускал и
останавливал. Grafana: дашборд «Координатор». Терминал контейнера: страница узла → «Открыть терминал
контейнера», команда `rm -rf /` блокируется политикой и попадает в аудит.
